# 第5天：Evaluation、Trace 与成本

目标：理解今天的机制，并能在小型知识库 Agent 中指出它的落点。

## 1. 建立小而固定的评测集

先用 20 题：8 道直接事实题、4 道改写题、3 道多轮题、3 道无答案题、2 道文档提示注入题。给每题标注期望事实、期望证据、是否应拒答。工具协议、预算与权限用确定性故障测试单独检验。

数据集分调参集与留出集，例如 15/5。小样本只能反映这组样本，不代表全领域准确率。不能不断看留出答案后还声称它是独立验证。

## 2. 分层指标与口径

| 指标 | 定义 | 解释 |
|---|---|---|
| Hit@3 | 有证据题中 top3 至少命中一个期望片段的题数 / 有证据题数 | 与需要全部证据的 Recall 不同 |
| Recall@3 | 每题命中的期望片段数 / 该题全部期望片段数，再宏平均 | 期望集合必须事先标注 |
| 正确率 | 人工判定关键事实正确的可回答题 / 全部可回答题 | 系统错误也计失败，不能排除 |
| 拒答正确率 | 正确拒答的无答案题 / 无答案题数 | 避免只统计回答出来的题 |
| 引用有效率 | 来自本次已授权证据的引用 ID 数 / 返回引用 ID 数 | ID 有效不代表语义支持 |
| 工具成功率 | 无协议与执行错误的调用 / 工具尝试总数 | 空结果本身是成功执行 |
| 端到端延迟 | 从收请求到返回终态的时间 | 报样本量、p50、p95 和错误数 |
| token 成本 | 每次 API attempt 的计费 token 乘对应单价后求和 | 包括重试及工具轮次 |

少量样本不适合夸大 p95 稳定性；记录原始耗时更有用。人工检查“每个结论是否由引用支持”，比单纯检查 ID 是否存在更接近真实可信度。

## 3. Trace 如何落地

每个请求一个 traceId；记录模型 attempt、工具执行、校验结果、终态。字段包括 model、promptVersion、corpusVersion、durationMs、tokenUsage、toolName、chunkIds、errorCode。正文默认脱敏或不记录，禁止记录 API Key。

不记录模型隐藏推理。模型可以给出简短可见说明，但排查依赖的是可观察动作、结果和错误，而非猜测内部思考。

## 4. 成本控制

先限制并发 1、工具执行 2 次、模型逻辑调用 3 次、历史 4 回合、每次输出最多 600 token；按实际模型参数校验是否支持。预算检查在发请求前执行，实际用量在返回后结算。连接中断时可能已经计费，因此保守预留，不把失败自动当免费。

## 5. 失败定位顺序

API 鉴权/限流 → 文档是否存在且授权 → 检索结果与版本 → 工具协议 → 上下文是否截断 → 最终生成和引用。保留同一问题的改动前后记录，每次只改一个主要变量。
